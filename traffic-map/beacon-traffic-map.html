Beacon · PoV architecture note

Every connection to a tenant estate, and who dials whom

Nine traffic paths exist between Beacon and a customer's Azure and UpCloud estate. Eight are outbound from the side that owns the private network. One is inbound to Beacon, and it is a signed webhook. No VNet peering, no Private Link, no inbound port into the customer.

Should a Connection be subscription-level?

Yes for Azure, with the subscription as the default unit and resource group as an optional narrower scope. Account or sub-account for UpCloud. But a Connection is not one thing. Model it as three fields that are decided independently, because that is what makes the MongoDB Atlas comparison stop being confusing.

Identity

Who Beacon is when it calls the provider.

  • Azure: one multi-tenant Entra application registered by Beacon. The customer grants admin consent, which creates a service principal in their tenant. Authenticate with workload identity federation from the cell, so there is no client secret to store or rotate.
  • UpCloud: the customer creates a sub-account with restricted permissions and issues an API token. Stored in the cell's secret store only.
  • Read and write are always two identities, on both providers.

Scope

What that identity is allowed to see.

  • Azure: a role assignment of Reader on the subscription. Resource Graph and Monitor then work across everything in it. Resource group scope is allowed for a cautious pilot. Management group later, for the MSP segment.
  • UpCloud: permissions on the sub-account, per resource type and optionally per resource.
  • One tenant holds many Connections. Multiple subscriptions is the normal case, not the edge case.

Network path

How packets get there. This is the field Atlas peering lives in.

  • Control-plane APIs: public TLS endpoints. Identity plus scope is the whole security model. No peering.
  • Workloads: the probe dials out. Beacon never opens a connection into a VNet.
  • Private API servers or Log Analytics behind Private Link: see the table below. Peering stays an option we can add, not a prerequisite.

Why Atlas needs peering and Beacon does not

Atlas peers or Private Links into your VNet because the thing you consume from Atlas is a data plane: a database listener your application connects to, and you do not want that traffic on the public internet. Beacon consumes control-plane APIs, which Microsoft and UpCloud already expose publicly with identity-based access, and it consumes workload telemetry, which the probe pushes out. Nothing in a customer VNet has to accept a connection from us.

The Atlas pattern that does transfer is identity. Atlas authenticates to Azure with an Entra service principal the customer consents to, scoped by role assignment. That is exactly path 1.

Rules this diagram commits us to

Outbound by owner

Whoever owns the private side opens the connection. Beacon opens connections to public APIs. Probes open connections to Beacon. No exceptions in the PoV.

Two identities per provider

Read and write are separate credentials with separate scopes. The agent worker holds neither. It calls tools in the collector loop, which hold the read identity only.

Webhooks are hints

Path 3 never creates state on its own. It advances the collector loop's next tick for that scope. A lost webhook costs latency, never correctness.

One egress per cell

Each tenant cell has an allowlist: the two providers' API hosts, the model gateway, the notification targets. Nothing else resolves.
